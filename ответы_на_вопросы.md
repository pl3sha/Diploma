## 1. Что такое спрайт

Спрайт — это небольшое 2D-изображение персонажа или объекта, используемое в видеоиграх. В старых играх (NES, Game Boy) спрайты были очень маленькими — 16×16 или 32×32 пикселя — и содержали строго ограниченное количество цветов из-за аппаратных ограничений консолей.

Современные «пиксельные» спрайты сохраняют тот же визуальный стиль — чёткие пиксели, ограниченная палитра, плоские цвета без градиентов — но рисуются в большем разрешении для удобства использования в современных движках (Unity, Godot и др.).

В нашем проекте спрайты — это изображения персонажей (воины, маги, демоны, нежить и др.) размером 512×512 пикселей с белым фоном, собранные из открытых источников.

---

## 2. Почему все изображения 512×512 и только белый фон

**Размер 512×512:**

Stable Diffusion v1.5 обучена генерировать изображения размером 512×512 пикселей. Это её «родное» разрешение — при таком размере модель работает оптимально. Если подавать изображения другого размера, модель будет хуже обучаться или давать артефакты.

Поэтому все спрайты из датасета приводятся к единому размеру 512×512 с помощью скрипта `prepare_dataset.py`:
- Если спрайт не квадратный — обрезается до квадрата по меньшей стороне
- Масштабируется до 512×512 методом ближайшего соседа (NEAREST) — чтобы не размывать пиксели
- Результат сохраняется в папку `images/`

**Белый фон:**

Исходные спрайты часто имеют прозрачный фон (PNG с альфа-каналом). Stable Diffusion работает с RGB-изображениями без прозрачности. Поэтому прозрачность заменяется белым фоном.

Дополнительно белый фон нужен для того, чтобы модель «научилась» генерировать персонажей именно на белом фоне — это и есть часть стиля, который мы хотим получить на выходе.

## 3. Что такое диффузионная модель (подробно)

Диффузионная модель — это класс генеративных нейросетей, основанный на двух процессах:

**Прямой процесс (зашумление):**
Берётся реальное изображение и к нему постепенно добавляется случайный гауссовский шум — шаг за шагом, пока изображение полностью не превратится в белый шум. Этот процесс фиксирован математически и не обучается.

**Обратный процесс (денойзинг):**
Нейросеть учится делать обратное — по зашумлённому изображению и текстовому описанию предсказывать, какой шум был добавлен на текущем шаге. Если повторить это много раз, начиная с чистого шума, нейросеть постепенно «вылепливает» изображение из шума.

**Почему это работает:**
Модель не генерирует пиксели напрямую, а итеративно убирает шум. Это даёт высокое качество и разнообразие генераций. Количество шагов (steps) — это сколько итераций денойзинга выполняется при генерации. Больше шагов = лучше качество, но дольше.

---

## 4. Что такое Stable Diffusion (подробно)

Stable Diffusion — это конкретная реализация диффузионной модели, разработанная компанией Stability AI в 2022 году. Версия v1.5 разработана совместно с RunwayML.

**Архитектура состоит из трёх компонентов:**

1. **Text Encoder (CLIP)** — преобразует текстовый промт в числовой вектор (эмбеддинг). Этот вектор описывает смысл текста в математическом пространстве.

2. **U-Net** — основная нейросеть с 860 млн параметров. Принимает зашумлённое изображение и текстовый эмбеддинг, предсказывает шум который нужно убрать. Именно в слоях U-Net и работает LoRA.

3. **VAE (Variational Autoencoder)** — кодирует изображение в компактное латентное пространство меньшего размера (64×64 вместо 512×512) и декодирует обратно. Это ускоряет работу в 8 раз — диффузия происходит в латентном пространстве, а не в пространстве пикселей.

**Почему выбрана SD v1.5:**
- Полностью открытый код и веса
- Минимальные требования к VRAM (4 ГБ для инференса)
- Наибольшая экосистема инструментов для LoRA-обучения
- Тысячи готовых LoRA-моделей как референс

## 5. Что такое LoRA (подробно)

LoRA (Low-Rank Adaptation) — метод эффективного дообучения больших нейросетей, предложенный Microsoft в 2021 году.

**Проблема которую решает LoRA:**
Полное дообучение SD v1.5 требует обновления всех 860 млн параметров U-Net. Это:
- Требует столько же VRAM сколько обучение с нуля (~24+ ГБ)
- Занимает дни или недели
- При малом датасете приводит к катастрофическому забыванию — модель «забывает» всё чему научилась на миллиардах изображений

**Как работает LoRA математически:**
Каждый линейный слой нейросети — это матрица весов W размером, например, 1024×1024 (≈1 млн параметров).

LoRA не изменяет W. Вместо этого добавляются две маленькие матрицы:
- Матрица A размером 1024×r
- Матрица B размером r×1024

где r — это «ранг» (rank), обычно 4, 8, 16, 32, 64.

При инференсе результат вычисляется как:
```
выход = W × вход + (A × B) × вход × scale
```

Матрица W заморожена. Обучаются только A и B — это в сотни раз меньше параметров.

**Пример для нашего проекта:**
- W: 1024×1024 = 1 048 576 параметров
- A + B при rank=32: 1024×32 + 32×1024 = 65 536 параметров (в 16 раз меньше)

Итого LoRA обучает ~2% от общего числа параметров модели.

**Результат:** файл 36 МБ вместо 4 ГБ, обучение 4 часа вместо недель.

## 6. Алгоритм обучения (подробно)

Обучение LoRA для Stable Diffusion следует алгоритму денойзинг-диффузии (DDPM):

**На каждом шаге:**

1. Из датасета случайно выбирается пара (изображение, текстовое описание)

2. Изображение кодируется через VAE в латентное представление (64×64)

3. Случайным образом выбирается временной шаг t (от 1 до 1000) — это «сколько шума добавить»

4. К латентному представлению добавляется гауссовский шум согласно расписанию шумов (noise scheduler). Зашумлённое изображение обозначается x_t

5. Текст кодируется через CLIP Text Encoder в эмбеддинг

6. U-Net (с добавленными LoRA-матрицами) принимает x_t, временной шаг t и текстовый эмбеддинг, и предсказывает шум ε_pred

7. Вычисляется функция потерь (loss) — среднеквадратичная ошибка между предсказанным и реальным шумом:
   ```
   loss = MSE(ε_pred, ε_real)
   ```

8. Через обратное распространение ошибки (backpropagation) обновляются только параметры LoRA-матриц A и B. Параметры W заморожены и не меняются.

9. Шаги 1–8 повторяются тысячи раз.

**Параметры нашего обучения:**
- 507 изображений в датасете
- 5 повторений датасета за эпоху (num_repeats=5)
- 15 эпох
- ~2535 шагов за эпоху (507 × 5)
- Всего ~38 025 шагов обучения

## 7. Что такое kohya_ss (подробно)

kohya_ss — это графический инструмент (GUI) для обучения LoRA-моделей, созданный японским разработчиком kohya. Является стандартом в сообществе для обучения LoRA под Stable Diffusion.

**Что делает kohya_ss внутри:**
- Читает изображения и текстовые описания из папки датасета
- Запускает цикл обучения (описан выше)
- Поддерживает оптимизаторы (AdamW, Adafactor, 8-bit Adam для экономии VRAM)
- Автоматически сохраняет чекпоинты после каждой эпохи
- Выводит loss в реальном времени

**Ключевые параметры нашего обучения:**

| Параметр | Значение | Пояснение |
|----------|----------|-----------|
| max_train_epochs | 15 | Сколько раз пройти весь датасет |
| num_repeats | 5 | Сколько раз повторить каждое изображение за эпоху |
| train_batch_size | 1 | Сколько изображений обрабатывается за один шаг |
| learning_rate | 1e-4 | Скорость обновления весов |
| network_dim (rank) | 32 | Ранг LoRA-матриц |
| network_alpha | 16 | Масштаб применения LoRA |
| optimizer | AdamW8bit | 8-битный оптимизатор для экономии VRAM |
| mixed_precision | bf16 | Смешанная точность для ускорения |

**Шагов за эпоху:**
507 изображений × 5 повторений ÷ 1 (batch size) = 2535 шагов/эпоху

**Результат:** файл `custom_8bit_v2.safetensors` размером 36 МБ

## 8. Почему LoRA — отдельный файл и как она связана с основной моделью

**Почему отдельный файл:**

LoRA не изменяет основную модель. Это набор дополнительных матриц (A и B для каждого слоя U-Net), сохранённых отдельно. Основная модель SD v1.5 (4 ГБ) остаётся нетронутой.

**Как они соединяются:**

При загрузке LoRA её матрицы добавляются к соответствующим слоям U-Net в оперативной памяти GPU. Веса не перезаписываются — они суммируются:
```
W_effective = W_frozen + A × B × scale
```

Когда LoRA выгружается — U-Net возвращается в исходное состояние.

**Как это работает в нашем бэкенде:**

```python
# Базовая модель — генерация без стиля
pipe.unload_lora_weights()   # LoRA отключена
result = pipe(prompt=...)    # U-Net работает с оригинальными весами W

# Генерация с нашей LoRA
pipe.load_lora_weights("custom_8bit_v2.safetensors")  # LoRA подключена
result = pipe(prompt=...)    # U-Net работает с W + A×B

# Переключение на другую LoRA
pipe.unload_lora_weights()   # убрать текущую
pipe.load_lora_weights("public_pixel_art.safetensors")  # подключить другую
```

Именно поэтому в системе можно переключаться между тремя режимами (base / public / custom) без перезапуска сервера — модель одна, LoRA меняется на лету.

## 9. Стек веб-системы и почему

**Backend: FastAPI (Python)**

- FastAPI — современный асинхронный веб-фреймворк для Python
- Выбран потому что: вся ML-экосистема (PyTorch, diffusers, transformers) — на Python; FastAPI даёт минимальный overhead и автоматическую документацию API
- Альтернатива Flask медленнее и не поддерживает async из коробки

**ML-библиотека: Hugging Face diffusers**

- Официальная Python-библиотека для работы с диффузионными моделями
- Предоставляет готовые методы `load_lora_weights()` / `unload_lora_weights()`
- Поддерживает SD v1.5 напрямую

**Frontend: React + Vite**

- React — компонентный подход, удобен для интерактивного интерфейса
- Vite — быстрый сборщик, заменяет устаревший Webpack
- Axios — HTTP-клиент для запросов к бэкенду
- Альтернативы (Vue, Angular) дали бы аналогичный результат, React выбран как наиболее распространённый

**Коммуникация: REST API + Base64**

- Фронтенд отправляет POST-запрос на `/generate` с промтом и параметрами
- Бэкенд возвращает изображение в виде Base64-строки в JSON
- Base64 выбран для простоты — не нужен отдельный файловый сервер

## 10. Как работает веб-система (подробно)

**Общая схема:**
```
Пользователь → Frontend (React) → Backend (FastAPI) → Stable Diffusion + LoRA → Изображение
```

**Шаг за шагом:**

1. **Пользователь** вводит текстовое описание в поле ввода, выбирает модель (base / public / custom), количество шагов (10–50) и размер (80 или 128 пикселей).

2. **Frontend** отправляет POST-запрос на `http://localhost:8000/generate`:
   ```json
   {
     "prompt": "green orc warrior with axe",
     "model_type": "custom",
     "steps": 30,
     "output_size": 128
   }
   ```

3. **Backend** получает запрос, вызывает функцию `switch_lora()`:
   - Если текущая LoRA не совпадает с запрошенной — выгружает старую и загружает нужную
   - Если запрошена "base" — выгружает LoRA совсем

4. **Backend** формирует полный промт добавляя префикс и суффикс:
   ```
   "pixel art sprite, 8-bit character, green orc warrior with axe,
   NES style, retro game, simple flat colors, pixelated,
   white background, sprite sheet character"
   ```

5. **Stable Diffusion** запускает процесс генерации:
   - CLIP кодирует промт в эмбеддинг
   - U-Net (с активной LoRA) итеративно убирает шум за N шагов
   - VAE декодирует латентное представление в изображение 512×512

6. **Backend** постобрабатывает изображение:
   - Масштабирует 512×512 → 128×128 методом NEAREST (сохраняет пиксельность)
   - Накладывает белый фон если есть прозрачность
   - Сохраняет PNG в папку `history/`
   - Кодирует в Base64

7. **Backend** возвращает JSON:
   ```json
   {
     "image": "iVBORw0KGgoAAAANSUhEUgAA...",
     "prompt": "pixel art sprite, 8-bit character...",
     "model": "custom",
     "size": 128
   }
   ```

8. **Frontend** декодирует Base64 и отображает изображение. Пользователь может сохранить его как PNG.

**Дополнительные эндпоинты:**
- `GET /health` — статус сервера, какая LoRA активна, доступна ли CUDA
- `GET /history` — последние 20 сгенерированных изображений

**Режим разработки vs продакшен:**
- В режиме разработки frontend работает на порту 3000, запросы проксируются на порт 8000 через Vite proxy
- В продакшене (`npm run build`) статические файлы из `frontend/dist/` раздаются самим FastAPI через StaticFiles middleware — отдельный запуск frontend не нужен

## 11. Метод NEAREST (ближайший сосед)

При уменьшении изображения с 512×512 до 128×128 нужно выбрать метод интерполяции — алгоритм определяющий цвет каждого нового пикселя.

**Стандартные методы:**
- **BILINEAR / BICUBIC** — усредняют соседние пиксели, дают плавный результат. Для фотографий это хорошо, для пиксель-арта — плохо: края размываются, чёткость теряется.
- **NEAREST (ближайший сосед)** — каждый новый пиксель берёт цвет ближайшего исходного пикселя без усреднения. Результат — чёткие границы, пиксели остаются "квадратными".

**Почему NEAREST для пиксель-арта:**

Пиксель-арт намеренно состоит из чётких квадратных пикселей — это часть его стиля. Если применить BILINEAR, чёткие границы превратятся в размытые переходы и изображение потеряет пиксельный характер.

В коде бэкенда:
```python
image = image.resize((128, 128), Image.NEAREST)
```

Тот же метод используется в `prepare_dataset.py` при подготовке датасета — чтобы исходные спрайты тоже не размывались при масштабировании до 512×512.

## 12. За что отвечает ползунок шагов на веб-сервисе

Ползунок управляет количеством шагов денойзинга (inference steps) при генерации изображения.

**Как это работает:**
Stable Diffusion начинает с чистого шума и итеративно «вычищает» его, делая предсказание на каждом шаге. Чем больше шагов — тем точнее и детализированнее результат, но тем дольше генерация.

| Шаги | Время генерации (RTX 3070) | Качество |
|------|---------------------------|----------|
| 10   | ~5 сек  | Черновое, артефакты |
| 25   | ~12 сек | Приемлемое |
| 50   | ~25 сек | Хорошее |

**Диапазон 10–50** выбран как разумный компромисс — меньше 10 шагов даёт слишком плохой результат, больше 50 не даёт заметного прироста качества но сильно увеличивает время ожидания.

В коде бэкенда значение передаётся напрямую в пайплайн:
```python
result = pipe(
    prompt=full_prompt,
    num_inference_steps=request.steps,  # значение с ползунка
    ...
)
```

## 13. Переключение между тремя моделями без перезапуска сервера

Это одна из ключевых архитектурных особенностей системы.

**Три режима:**
- `base` — чистая Stable Diffusion v1.5 без каких-либо адаптеров
- `public` — SD v1.5 + публичная LoRA (PixelArt Redmond)
- `custom` — SD v1.5 + наша обученная LoRA (custom_8bit_v2.safetensors)

**Как реализовано:**

Модель SD v1.5 загружается в GPU один раз при старте сервера и остаётся там всё время. Это тяжёлая операция — занимает ~30 секунд и ~4 ГБ VRAM.

LoRA — лёгкий файл (36 МБ). Её можно быстро «пристегнуть» к модели и «отстегнуть» без перезагрузки основных весов.

В бэкенде за это отвечает функция `switch_lora()`:

```python
current_lora = None  # глобальная переменная — какая LoRA сейчас активна

def switch_lora(model_type: str) -> None:
    global current_lora
    if model_type == current_lora:
        return  # уже нужная LoRA — ничего не делаем

    if current_lora is not None:
        pipe.unload_lora_weights()  # отстегнуть текущую LoRA
        current_lora = None

    if model_type != "base":
        lora_path = _resolve_lora_path(model_type)  # найти файл LoRA
        pipe.load_lora_weights(str(lora_path))       # пристегнуть новую LoRA
        current_lora = model_type
```

**Что происходит при смене модели:**
1. Старая LoRA выгружается — U-Net возвращается к оригинальным весам W
2. Новая LoRA загружается — к U-Net добавляются матрицы A×B новой LoRA
3. Операция занимает ~1-2 секунды (не 30 как при старте)

**Оптимизация:** если пользователь делает несколько запросов подряд с одной и той же моделью — `switch_lora()` сразу возвращается (`return`) без лишних операций. Текущая активная модель хранится в глобальной переменной `current_lora`.
